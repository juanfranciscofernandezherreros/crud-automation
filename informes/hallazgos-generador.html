Hallazgos y mejoras del generador

Qué apareció al usar el generador CRUD contra un esquema real de más de 270 columnas (un mensaje de reporte tipo EMIR/SFTR) y, después, contra peticiones de filtrado y una segunda vía de definición por JSON — y cómo se corrigió cada limitación en crud_generator/.

Contexto

El caso de prueba: 273 campos reales

El generador se había probado siempre con entidades de ejemplo pequeñas (3 a 10 campos: Producto, OperacionFinanciera, FondoInversion...). Al pedirle que reprodujera un esquema real de reporting regulatorio con 273 columnas — tipos string, timestamp, int y decimal(p,s) con precisión variable, dos columnas como clave primaria compuesta, y un par de columnas con valor por defecto — aparecieron cuatro limitaciones de expresividad y, al generar el proyecto completo, un error de compilación real que ningún caso de prueba anterior había disparado.

Hallazgo 1 · Precisión y escala fijas

Todos los decimal se generaban como DECIMAL(19,4)mejora

El esquema original define columnas como decimal(38,19) o decimal(31,13), pero el generador solo conocía un decimal genérico mapeado siempre a DECIMAL(19,4) / BigDecimal. Cualquier valor con más de 4 decimales se habría truncado al insertarse en PostgreSQL.

Mejora

Nuevas reglas precision=N:scale=N (solo válidas junto a decimal, y siempre en pareja) que generan el tipo SQL exacto:

importe:decimal:precision=31:scale=13
→ DECIMAL(31, 13)  en Flyway y BigDecimal en Java
Hallazgo 2 · Sin tipo texto libre

Todo string era VARCHAR(255)mejora

La columna json_data del esquema guarda JSON de longitud variable. Como único tipo de texto disponible era string (VARCHAR(255) salvo que se indicara max=N), la única forma de acomodarlo era un límite arbitrario (p. ej. max=10000) que sigue sin ser un límite real.

Mejora

Nuevo tipo text → columna TEXT de PostgreSQL sin límite de longitud. Las reglas min=/max= siguen funcionando, pero se validan con CHECK char_length(...) en vez de acortar el tipo de columna.

json_data:text:not_blank
→ json_data TEXT NOT NULL CHECK (btrim(json_data) <> '')
Hallazgo 3 · Sin valores por defecto

Los default_value del esquema se perdíanmejora

Dos columnas del esquema (lstusr y islegacy) tienen un valor por defecto real ('usr' y 'false'). El generador no tenía ningún concepto de "default"; la única opción era omitirlo y dejar que la aplicación fallara al no recibir ese campo, o marcarlo como obligatorio en el DTO (forzando al cliente HTTP a enviarlo siempre, que es justo lo contrario de lo que significa un default).

Mejora

Nueva regla default=valor. Genera tres cosas a la vez, y aquí apareció un matiz no evidente: no basta con poner DEFAULT 'usr' en la migración Flyway, porque Hibernate por defecto incluye todas las columnas en el INSERT — si el DTO llega con ese campo en null, Hibernate inserta NULL explícito y el DEFAULT de PostgreSQL nunca llega a aplicarse.

CapaQué genera
Java (entidad)private String lstusr = "usr"; — valor de partida si se construye directamente.
Flyway (SQL)lstusr VARCHAR(255) NOT NULL DEFAULT 'usr'
Entidad JPA@DynamicInsert — Hibernate omite del INSERT las columnas que lleguen en null, dejando que el DEFAULT de PostgreSQL se aplique de verdad.
Hallazgo 4 · Sin clave compuesta

refitid + refitidctrl son la clave primaria real del esquemamejora

El generador solo entiende un id autonumérico simple (SERIAL PRIMARY KEY vía @GeneratedValue(IDENTITY)), como cualquier CRUD JPA estándar. El esquema real usa dos columnas como clave (primary_key: true en ambas). Marcarlas como unique por separado no es equivalente: permite que el par (refitid, refitidctrl) se repita combinando valores ya usados individualmente en otra fila.

Mejora

Nueva regla composite_unique=grupo: los campos que comparten el mismo nombre de grupo generan una única restricción UNIQUE multi-columna, tanto en Flyway como en @Table(uniqueConstraints = ...) de la entidad JPA.

refitid:string:not_blank:composite_unique=refit_key
refitidctrl:string:not_blank:composite_unique=refit_key

→ CONSTRAINT uq_reportederivados_refit_key UNIQUE (refitid, refitidctrl)
Límite que queda: refitid+refitidctrl no pueden ser la clave primaria real de la tabla — JPA/Hibernate solo soporta eso con @EmbeddedId, un patrón distinto al que usa todo este generador. Se mantiene el id autonumérico técnico y la pareja queda como restricción de negocio (UNIQUE compuesta) adicional. Es una limitación conocida, no un bug.
Hallazgo 5 · Bug real de compilación

Límite de 255 parámetros de constructor de la JVMfix

Con las cuatro mejoras anteriores aplicadas, el proyecto de 273 campos se generó pero no compilaba:

[ERROR] COMPILATION ERROR :
[ERROR] .../entity/ReporteDerivado.java:[23,1] too many parameters

Causa: la entidad usa @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder de Lombok. @AllArgsConstructor genera un constructor con un parámetro por campo — 273 campos de negocio + id + version = 275 parámetros. La especificación de la JVM (JVMS §4.11) limita cualquier método o constructor a 255 parámetros, contando la referencia implícita al objeto (this). javac rechaza la clase antes incluso de llegar a ejecutarse nada.

Ningún caso de prueba anterior lo había disparado porque ninguna entidad de ejemplo se había acercado nunca a 250 campos.

Corrección

crud_generator/fields.py añade exceeds_constructor_param_limit(attrs) (umbral 254, dejando margen para id+version). generator.py y ports_generator.py la consultan antes de renderizar la entidad; si se supera, templates.py / ports_templates.py omiten @AllArgsConstructor y @Builder —queda @NoArgsConstructor + @Getter/@Setter, que es todo lo que JPA necesita y todo lo que MapStruct necesita para mapear DTO→entidad por setters cuando no hay builder disponible.

EntidadCampos + version@AllArgsConstructor / @Builder
Producto (ejemplo típico)3Se incluyen (muy por debajo del límite)
ReporteDerivado (este caso)275Se omiten automáticamente

Verificado generando y compilando (mvn -DskipTests compile) el proyecto de 273 campos, y con tests/test_templates.py cubriendo ambos casos (entidad normal vs. entidad ancha) para que no vuelva a pasar desapercibido.

Hallazgo 6 · Bug real encontrado en producción (Docker)

Ordenar por una propiedad inexistente devolvía 500 con stack tracefix

Con crud-reportederivado ya levantado en Docker (docker compose up, PostgreSQL + app reales, no un mock) y 15 filas insertadas, una petición GET /api/reportederivados?sort=string — string es el valor de ejemplo que Swagger UI rellena por defecto en un parámetro de tipo texto — devolvía 500 con una PropertyReferenceException completa filtrada al cliente:

org.springframework.data.mapping.PropertyReferenceException:
No property 'string' found for type 'ReporteDerivado'

GlobalExceptionHandler no tenía ningún @ExceptionHandler para esa excepción, así que Spring dejaba pasar el error tal cual hasta el cliente. Ningún proyecto de ejemplo anterior lo había disparado porque nadie prueba manualmente ?sort= con un valor inventado contra un servicio real.

Corrección

Nuevo @ExceptionHandler(PropertyReferenceException.class) en templates.py y ports_templates.py que responde 400 con un mensaje claro ("Propiedad de ordenación no válida: string"). De paso, se corrigió el mismo ruido cosmético en docker-compose.yml: el healthcheck pg_isready -U $POSTGRES_USER sin -d intentaba conectar a una base de datos llamada igual que el usuario (convención por defecto de libpq) y llenaba el log de FATAL: database "app_user" does not exist cada 5 segundos — inofensivo, pero confuso; ahora es pg_isready -U ... -d $POSTGRES_DB.

Hallazgo 7 · Pedido explícito del usuario

Filtrado genérico por cualquier campo, combinado con paginaciónfeature

El generador solo paginaba (page/size/sort); no existía forma de filtrar el listado por ningún campo. Se añadió un filtrado por igualdad exacta sobre cualquier campo de la entidad, vía query params, combinable con la paginación:

GET /api/reportederivados?cntrctsts=ACTV&page=0&size=3
GET /api/reportederivados?refitid=REFIT-2026-007

En generación se conoce el tipo Java real de cada campo, así que en vez de un filtro genérico basado en reflexión se genera una clase {Entity}Specifications con un Specification<Entity> de Spring Data (JPA Criteria) y un case por campo que convierte el String del query param al tipo correcto (Integer.valueOf, new BigDecimal(...), LocalDate.parse(...), etc.) antes de comparar — sin reflexión, con conversión de tipos comprobada en compilación. Los query params que no coinciden con ningún campo (incluidos page/size/sort) se ignoran silenciosamente.

Las tres arquitecturas

ArquitecturaDónde vive el filtro
layered{Entity}Specifications junto al repositorio; el controller la invoca directamente y pasa el Specification al service.
hexagonal / cleanPageQuery del dominio gana un campo Map<String,String> filters (tipo JDK puro, no rompe el aislamiento del dominio); el Specification solo se construye dentro del adaptador de persistencia ({Entity}JpaSpecifications), donde ya se permiten tipos JPA.

Efecto secundario esperado: un valor de filtro con formato inválido (?othrmstragrmtvrsn=no-es-un-numero sobre un campo int) lanza NumberFormatException/DateTimeParseException. Se añadió el mismo tipo de @ExceptionHandler que en el Hallazgo 6 para devolver 400 en vez de 500.

Hallazgo 8 · Pedido explícito del usuario

Definir entidades por JSON, sin la restricción de caracteres del DSL de textofeature

La única forma de definir una entidad era la cadena nombre:tipo:regla,... por línea de comandos. Funciona bien para entidades pequeñas, pero tiene un límite de expresividad concreto: el propio delimitador (:) no puede aparecer dentro del valor de una regla. Un default de tipo fecha/hora (2026-08-11T10:00:00) o cualquier valor con : obligaba a reescribirlo o perdía información.

Mejora

Nueva vía de entrada python generate_crud.py --json <fichero> [--architecture ...], alternativa a la cadena por CLI. Cada campo es un objeto JSON con sus reglas como claves (required, not_blank, min, max, precision, scale, composite_unique, default...). parse_attributes_from_fields() valida directamente sobre el JSON en vez de reconstruirlo como texto delimitado, así que default deja de tener restricción de caracteres — las comprobaciones de coherencia y el ensamblado final del atributo se extrajeron a funciones compartidas entre el DSL de texto y el JSON, para no duplicar reglas de validación.

{
  "entity": "FondoInversion",
  "architecture": "hexagonal",
  "package": "com.example.fondos",
  "fields": [
    {"name": "isin", "type": "string", "max": 12, "not_blank": true, "unique": true},
    {"name": "patrimonio", "type": "decimal", "precision": 18, "scale": 2, "default": 0},
    {"name": "activo", "type": "boolean", "required": true, "default": true}
  ]
}

Verificado con examples/fondoinversion.json (25 campos reales de un microservicio de fondos de inversión): generado vía --json --architecture hexagonal y compilado con mvn verify, produce el mismo resultado que la ruta equivalente por CLI.

Bug encontrado al usarlo con package/endpoints propios: generator.py ya pasaba base_package/endpoints a documentation.get_documentation_html, templates.get_controller/get_controller_test y ports_generator.generate_ports_project_from_attrs, pero esas funciones destino todavía no los aceptaban como parámetro — cualquier generación vía --json que indicara package o endpoints rompía con TypeError antes de escribir un solo fichero, en las tres arquitecturas. Corregido propagando el parámetro en toda la cadena y filtrando métodos/imports/mocks del controller y su test según los endpoints pedidos (commit aa47a56).
Resultado

Estado final verificado

python -m pytest -q → 67 tests en verde (7 subtests), incluyendo mvn verify real sobre los proyectos de aceptación (uno ejercitando composite_unique, default, text, decimal(precision,scale) y el filtrado a la vez) y tests/test_json_schema.py cubriendo la ruta --json. El proyecto crud-reportederivado/ con los 273 campos completos compila limpio y corre en Docker (docker compose up) con las 15 filas de prueba insertadas, paginación, filtrado y los dos manejadores de error nuevos verificados en vivo contra la API real. crud-fondoinversion-hexagonal/ (25 campos, generado vía --json) compila igual en arquitectura hexagonal, confirmando que la vía JSON produce el mismo resultado que el DSL de texto.
