Enum y relaciones ahora en hexagonal y clean

Tras la sesión anterior (overwrite guard, migraciones incrementales, CI/observabilidad, enum, relaciones multi-entidad, JSON Schema y Cucumber+Allure), se pidió una valoración del generador. La brecha más grande señalada fue que enum y las relaciones reference solo funcionaban con architecture: "layered". Esta sesión cierra esa brecha para hexagonal y clean.

Contexto

Por qué no era trivial reutilizar lo ya hecho

En layered, la clase {Entity}.java es a la vez el modelo que ve la API y la entidad JPA: una reference se representa igual en todas partes salvo en el DTO. En hexagonal/clean hay tres representaciones distintas de la misma entidad — el modelo de dominio (objeto plano, sin JPA, sin acceso a repositorios), la entidad JPA ({Entity}JpaEntity, en el paquete de persistencia) y el DTO — y el dominio no puede resolver una referencia por sí solo porque no tiene forma de consultar un repositorio. Portar la función tal cual habría compilado pero apuntado al modelo de dominio equivocado (Cliente en vez de ClienteJpaEntity) en la entidad JPA.

Diseño elegido

CapaCampo cliente (reference)
Dominio (Pedido)Integer clienteId — igual que el DTO; sin acceso a repositorio, no puede resolver el objeto.
Entidad JPA (PedidoJpaEntity)@ManyToOne a ClienteJpaEntity (no a Cliente, el dominio).
DTOInteger clienteId.

Como dominio y DTO quedan simétricos (los dos usan clienteId), {Entity}WebMapper no necesita ningún @Mapping especial — MapStruct los empareja solo. Solo hacen falta cambios en {Entity}PersistenceMapper (ignora cliente en ambas direcciones, igual que el mapper de DTO en layered) y en {Entity}PersistenceAdapter, que resuelve la referencia contra el repositorio JPA correspondiente justo antes de guardar — en save(), el único punto de escritura del puerto, así que cubre alta y actualización con el mismo código.

Hallazgo 1 · Bug real de compilación

PedidoService llamaba a getCliente()/setCliente(), que no existenfix

La primera generación+compilación de un proyecto hexagonal con relaciones falló:

[ERROR] PedidoService.java:[36,39] cannot find symbol
  symbol:   method getCliente()
  location: variable replacement of type com.miempresa.ventas.domain.model.Pedido

generate_domain_update_statements() (compartida entre update/patch del Service puro de hexagonal/clean) construye el nombre del getter/setter a partir de camel_name sin más — correcto para un campo normal, pero para una reference el dominio en realidad expone getClienteId()/setClienteId(), no getCliente()/setCliente(). Ningún test cubría esta función hasta ahora.

Corrección

fields.py: cuando attr["type"] == "reference", el sufijo del accessor lleva Id añadido. Cubierto con test_domain_update_statements_use_the_id_suffixed_accessor en tests/test_fields.py.

Hallazgo 2 · Bug real de compilación

El test del controller de ports se quedó sin la variable que usafix

[ERROR] PedidoControllerTest.java:[45,9] cannot find symbol
  symbol:   variable dto

Al extender ports_generator.py se copió, por descuido, la convención de nombre de variable (dto) que usan los steps de Cucumber de layered — pero ports_templates.get_controller_test() construye su DTO de prueba como createDTO, no como dto. Se detectó igual que el hallazgo anterior: al compilar el proyecto generado, no en los tests unitarios de Python (que no ejecutan javac).

Corrección

Se quitó el variable_name="dto" pasado de más en ports_generator.py. Cubierto con test_ports_controller_test_builds_the_dto_as_createDTO en tests/test_templates.py, que fija explícitamente el nombre de variable esperado para que una futura reutilización cruzada no vuelva a mezclarlos.

Patrón que se repite: los dos bugs de esta sesión (y varios de la anterior) son inconsistencias de nombres entre capas que python -m pytest no detecta porque cada función de plantilla se prueba de forma aislada, con cadenas sueltas — el contrato real entre dos plantillas generadas (qué variable declara una, qué variable espera otra) solo se verifica compilando el proyecto completo con mvn. Por eso la regla del repositorio insiste en generar+compilar antes de dar una plantilla por válida, no solo correr la suite de Python.
Resultado

Estado final verificado

python -m pytest -q → 133 tests en verde, más la suite de aceptación (mvn verify real sobre layered/hexagonal/clean, sin las features nuevas, para confirmar que el refactor de ports_generator.py no rompió el caso base).

Verificación no repetida en esta sesión: la sesión anterior sí probó las relaciones end-to-end contra Docker real (Postgres, FK real, 404 con id inexistente, PATCH parcial) para layered. Para hexagonal/clean, Docker Desktop no estaba disponible en esta máquina en el momento de verificar, así que la confianza aquí viene de compilación real + tests unitarios/MVC reales, no de un docker compose up con peticiones HTTP de verdad. La lógica del adaptador de persistencia es estructuralmente idéntica a la ya probada en layered (mismo patrón resolver-o-404), pero queda pendiente una verificación con Docker si se quiere el mismo nivel de confianza.

Con esto, enum y las relaciones reference del formato multi-entidad funcionan igual en las tres arquitecturas que ofrece el generador. Sigue pendiente lo que ya se señaló como fuera de alcance: el DSL de texto (sin JSON) no soporta ninguno de los dos, ni hay @OneToMany/@ManyToMany, solo @ManyToOne.
