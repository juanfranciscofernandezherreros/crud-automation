@OneToMany desde el lado "uno" de la relación

Tras cerrar la brecha de enum/reference en hexagonal y clean, quedaba señalado que el generador solo modelaba @ManyToOne: "un Cliente tiene muchos Pedidos" no se podía consultar desde el lado Cliente. Esta sesión lo cierra.

Diseño

Qué se genera, y qué se decidió no generar

El lado "uno" de una reference (p.ej. Cliente, al que apunta Pedido.cliente) recibe dos cosas:

QuéDónde
@OneToMany(mappedBy = "cliente", fetch = FetchType.LAZY) private List<Pedido> pedidos;Entidad JPA (Cliente.java en layered, ClienteJpaEntity.java en hexagonal/clean, apuntando a PedidoJpaEntity) — grafo de persistencia correcto y navegable.
Filtro GET /api/pedidos?clienteId=5PedidoSpecifications/PedidoJpaSpecifications: cb.equal(root.get("cliente").get("id"), Integer.valueOf(value)), navegando a la asociación sin join explícito.

Deliberadamente no se incrusta la colección en el dominio, los DTOs ni la respuesta de Cliente. Dos razones: en hexagonal/clean el dominio no tiene acceso a un repositorio para poblarla (igual que ya pasaba con el lado @ManyToOne, resuelto en la sesión anterior), y en cualquier arquitectura incrustar una colección sin paginar en la respuesta de un recurso es un antipatrón conocido (tamaño de payload no acotado, riesgo de N+1 si Hibernate la carga entera). La vía soportada para "los pedidos de un cliente" es el filtro genérico ya existente en el generador — el mismo mecanismo que cualquier otro campo, solo que ahora también funciona para una reference, que antes se ignoraba silenciosamente en generate_specification_filter_cases.

Tampoco se genera @ManyToMany: no se pidió explícitamente y añade una entidad de unión (tabla intermedia) que es un salto de complejidad mayor que este cambio.

Implementación

De dónde sale la lista de "quién me referencia"

Nueva función fields.compute_inverse_relations(entities): recorre el entities del JSON multi-entidad una vez y devuelve, para cada entidad, la lista de (entidad_que_la_referencia, campo). Una autoreferencia (p.ej. Categoria.padre → Categoria) no genera una relación inversa hacia sí misma. generate_entity_fields() gana un parámetro inverse_relations que añade el bloque @OneToMany al final de la entidad; reference_type_suffix (ya existente desde la sesión anterior) hace que en hexagonal/clean la colección apunte a PedidoJpaEntity y no a Pedido (el dominio).

Como Cliente y Pedido siempre viven en el mismo paquete (el de entidad en layered, el de persistencia en hexagonal/clean), la clase referenciada en el @OneToMany no necesita import — solo hace falta añadir import java.util.List;, condicional a que la entidad tenga alguna relación inversa.

Resultado

Estado final verificado

python -m pytest -q → 139 tests en verde, más la suite de aceptación completa (mvn verify real sobre layered/hexagonal/clean sin las features nuevas, para confirmar que no se rompió el caso base).

ArquitecturaVerificación
layeredGenerado (Cliente + Pedido) + mvn test-compile + 18 tests unitarios/controller en verde. Cliente.java con List<Pedido> pedidos, PedidoSpecifications con el case "clienteId" nuevo.
hexagonalGenerado + mvn test-compile + 16 tests en verde. ClienteJpaEntity.java con List<PedidoJpaEntity> pedidos.
cleanGenerado + mvn test-compile + 16 tests en verde. Mismo resultado que hexagonal, paquetes distintos.
No verificado con Docker real: Docker Desktop no estuvo disponible en esta máquina durante toda la sesión, así que no se pudo levantar el stack y comprobar GET /api/pedidos?clienteId=5 contra Postgres real con datos insertados — como sí se hizo para las relaciones @ManyToOne en layered en una sesión anterior. La confianza aquí viene de compilación real + tests unitarios/MVC reales; el patrón root.get(assoc).get("id") de Criteria API es estándar y ya se valida a nivel de tipos en la compilación, pero una verificación end-to-end queda pendiente si se quiere el mismo nivel de confianza que las demás features de esta sesión.
