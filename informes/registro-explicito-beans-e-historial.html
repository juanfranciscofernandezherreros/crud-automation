Registro explícito de Services, Mappers y Controllers como beans

Informe de arquitectura, justificación, riesgos, verificación y lectura cronológica del historial Git. Cambio preparado en la rama feature/explicit-bean-registration.

Resumen ejecutivo

El generador pasa de depender de component scanning para Services, Mappers y Controllers a construir explícitamente el grafo principal de la aplicación con @Bean. Los mappers MapStruct se generan sin componentModel = "spring"; los Services dejan de usar @Service; los Controllers conservan @RestController porque esa anotación define su semántica MVC, pero se excluyen del component scan y su instancia procede de un método @Bean.

La política se implementa en el punto común de escritura del generador, crud_generator/writer.py, para que se aplique de forma uniforme a layered, hexagonal y clean. El proyecto generado recibe un GeneratedBeanConfiguration.java que actúa como composition root explícito.

Antes y después

Antes

@Mapper(componentModel = "spring")
public interface UserMapper { ... }

@Service
public class UserServiceImpl { ... }

@RestController
public class UserController { ... }

Spring descubría estas piezas de forma implícita al escanear el classpath.

Después

@Mapper
public interface UserMapper { ... }

public class UserServiceImpl { ... }

@RestController
public class UserController { ... }

@Configuration
public class GeneratedBeanConfiguration {
    @Bean
    UserMapper userMapper() {
        return Mappers.getMapper(UserMapper.class);
    }

    @Bean
    UserServiceImpl userServiceImpl(UserRepository repository, UserMapper mapper) {
        return new UserServiceImpl(repository, mapper);
    }

    @Bean
    UserController userController(UserServiceImpl service) {
        return new UserController(service);
    }
}

Por qué es un buen cambio

  • Composition root visible: se puede leer en un único lugar qué objetos forman la aplicación y con qué dependencias se construyen.
  • Menos comportamiento implícito: una clase no entra accidentalmente en el contexto solo por llevar una anotación estereotipo y encontrarse dentro del paquete escaneado.
  • Arquitectura más controlable: Services y Mappers quedan como clases/interfaces Java ordinarias. Spring se concentra en la capa de composición, no invade la definición de cada pieza.
  • MapStruct desacoplado de Spring: los mappers usan @Mapper y se instancian con Mappers.getMapper(...). El contrato de mapping ya no depende del component model de Spring.
  • Wiring determinista: las dependencias se ven como parámetros de cada método @Bean, facilitando revisión y diagnóstico de ciclos o duplicados.
  • Coherencia entre arquitecturas: la regla se aplica desde un punto común. Esto encaja con el aprendizaje histórico del repositorio: los cambios duplicados entre templates.py y ports_templates.py ya provocaron derivas y motivaron el refactor DRY de shared_templates.py.
  • Mejor base para reglas futuras: al estar codificada en el generador, la convención deja de depender de que una persona o agente recuerde aplicarla manualmente.

Decisiones y trade-offs

  • @RestController se conserva: Spring MVC necesita identificar el handler. Para evitar doble registro, CrudApplication excluye los controllers del component scan y el bean explícito aporta la instancia.
  • Los repositorios Spring Data no se cambian: su generación mediante proxies de Spring Data sigue siendo una capacidad del framework, no un Service/Mapper/Controller de la aplicación.
  • En hexagonal/clean ya existía UseCaseConfiguration para el Service. La generación detecta clases ya construidas por configuraciones existentes y evita crear un bean duplicado.
  • Los persistence adapters siguen con su mecanismo actual porque no formaban parte de la regla solicitada.
  • La configuración generada crece con el número de entidades, pero ese crecimiento es explícito y generado automáticamente; no añade trabajo manual al consumidor del CRUD.

Implementación y verificación

Commit 0ed8cad: añade la política central en writer.py: transformación de anotaciones, exclusión de controllers del scan, descubrimiento de dependencias y regeneración de GeneratedBeanConfiguration.java.

Commit afd3034: añade tests/test_explicit_bean_registration.py. Comprueba que mapper/service/controller quedan registrados mediante beans y que un Service ya creado por UseCaseConfiguration no se duplica.

Además se realizó un smoke test local del writer con un CRUD mínimo: el resultado produjo los tres métodos @Bean esperados, eliminó componentModel="spring" y @Service, y añadió la exclusión de RestController al component scan. La suite Maven completa del repositorio no se ejecutó desde este entorno conectado; la prueba añadida queda preparada para la CI del repositorio.

Conclusión derivada del historial

El patrón dominante del repositorio es claro: cuando una regla importa, termina pasando de conocimiento implícito a una garantía ejecutable. Ocurrió con el límite de 255 parámetros, con las pruebas de proyectos generados, con la trazabilidad pre-push, con --verify y con el refactor DRY. Registrar Services, Mappers y Controllers mediante @Bean sigue exactamente esa línea: la arquitectura deja de depender de disciplina manual y pasa a estar impuesta por el propio generador.
